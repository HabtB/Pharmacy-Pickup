# Technical Debug Report: iOS Black Screen on App Relaunch
## Pharmacy Pickup App — Flutter 3.41 / iOS 26 / Xcode 26.3

**Date:** 2026-03-14 to 2026-03-15
**Device:** iPhone 12 (AneBaeley), iOS 26.3.1
**Flutter:** 3.41.4, Dart 3.11.1
**Xcode:** 26.3 (Build 17C529)

---

## 1. Problem Statement

The app launches perfectly via `flutter run` (debug mode). After swipe-killing the app from the iOS app switcher and tapping the icon to reopen, a **black screen with the Flutter debug banner** appears. The app never renders any Dart UI. This happens consistently, both with and without a USB debug connection.

---

## 2. Root Cause (Final Diagnosis)

### Primary Cause: iOS Debug Build JIT Limitation

**Flutter debug builds on iOS 14+ CANNOT cold-launch from the home screen without a debugger connection.**

This is not a bug — it is an iOS security restriction documented in Flutter's engine source code.

**Source:** `FlutterViewController.mm` (line 546 in Flutter engine):
```objc
// The engine displays this message when debug mode is launched without a debugger:
@"In iOS 14+, debug mode Flutter apps can only be launched from Flutter tooling, "
@"IDEs with Flutter plugins or from Xcode.\n\nAlternatively, build in profile or "
@"release modes to enable launching from the home screen."
```

**Technical explanation:**

```
┌─────────────────────────────────────────────────────────────────────┐
│                     HOW FLUTTER BUILDS WORK                         │
├─────────────────────┬───────────────────────────────────────────────┤
│ Debug Build         │ Uses JIT (Just-In-Time) compilation           │
│                     │ Dart code compiled on-the-fly at runtime      │
│                     │ Requires ptrace() to modify code pages        │
│                     │ ptrace() only available via debugserver        │
│                     │ → Needs Xcode/flutter run to provide debugger │
│                     │ → Home screen launch = NO ptrace = BLACK SCREEN│
├─────────────────────┼───────────────────────────────────────────────┤
│ Release Build       │ Uses AOT (Ahead-Of-Time) compilation          │
│                     │ Dart code pre-compiled to machine code         │
│                     │ Does NOT need ptrace()                         │
│                     │ → Home screen launch works perfectly           │
├─────────────────────┼───────────────────────────────────────────────┤
│ Profile Build       │ Hybrid: AOT compiled + profiling hooks         │
│                     │ Does NOT need ptrace()                         │
│                     │ → Home screen launch works perfectly           │
└─────────────────────┴───────────────────────────────────────────────┘
```

**The ptrace mechanism** (from `ptrace_check.cc` in Flutter engine):
```
// When an app is launched from a host workstation (e.g. via Xcode or
// "ios-deploy"), the process is already ptrace()-d by debugserver. However,
// when an app is launched from the home screen, it is not, so for debug builds
// we initialize the ptrace() relationship via PT_TRACE_ME if necessary.
//
// On iOS 14+, this self-ptrace fails due to security restrictions.
// Result: the Dart VM cannot start JIT compilation → black screen.
```

**Fix:**
```bash
# Instead of:
flutter run                    # Debug build — will black-screen on relaunch

# Use:
flutter run --release          # Release build — works from home screen
flutter run --profile          # Profile build — works from home screen + profiling
```

## 3. Secondary Issues Found and Fixed

While the debug build limitation was the primary cause, several real configuration issues were discovered and fixed during the investigation.

### 3.1 Outdated Impeller Setting (`FLTEnableImpeller: false`)

**File:** `ios/Runner/Info.plist`

**Problem:** The project had Impeller (Flutter's modern rendering engine) disabled, forcing the old Skia renderer. This was a leftover from when the project was created with an older Flutter version (pre-3.16). Since Flutter 3.16, Impeller is the default on iOS.

**Symptoms caused:**
- Slower app launch time (Skia Metal initialization is slower than Impeller on newer iOS)
- GPU sandbox deny errors (`AGXAcceleratorG13P_B0`) in system logs — Skia's Metal backend struggling with GPU resource acquisition
- Potential rendering issues with the new UIScene lifecycle (Impeller was designed for it)

**Before (broken):**
```xml
<!-- ios/Runner/Info.plist -->
<!-- BAD: This disables Impeller and forces the old Skia renderer.
     This was auto-generated by older Flutter templates (pre-3.16).
     Skia is slower to initialize, especially on cold relaunch,
     and causes GPU sandbox deny errors on newer iOS versions. -->
<key>FLTEnableImpeller</key>
<false/>
```

**After (fixed):**
```xml
<!-- ios/Runner/Info.plist -->
<!-- REMOVED the FLTEnableImpeller key entirely.
     When absent, Flutter defaults to Impeller (the modern renderer).
     Impeller is faster, designed for the UIScene lifecycle,
     and handles Metal GPU resources more reliably. -->

<!-- (key simply removed — no replacement needed) -->
```

**Result:** Launch time dropped from ~62s to ~17s on the same device.

### 3.2 Missing `SceneDelegate.swift`

**File:** `ios/Runner/SceneDelegate.swift` (did not exist)

**Problem:** Flutter 3.41's auto-migration tool rewrote `AppDelegate.swift` and `Info.plist` to use the new UIScene lifecycle, but it **never created `SceneDelegate.swift`** — even though Flutter's own app template for new projects includes one.

**Discovery:** Found by comparing Flutter's migration tool source code (`uiscene_migration.dart`) with the app template:

```
# Flutter's template for NEW projects includes this file:
/flutter/packages/flutter_tools/templates/app/ios.tmpl/Runner/SceneDelegate.swift

# But the migration tool (for EXISTING projects) only:
# 1. Rewrites AppDelegate.swift
# 2. Adds UIApplicationSceneManifest to Info.plist
# 3. Does NOT create SceneDelegate.swift  ← GAP IN MIGRATION TOOL
```

**Info.plist was pointing to the framework class directly:**
```xml
<!-- BAD: Points directly to Flutter's framework base class.
     New projects use a local subclass (Runner.SceneDelegate) instead.
     The base class may not handle all lifecycle scenarios correctly
     without the project-level subclass. -->
<key>UISceneDelegateClassName</key>
<string>FlutterSceneDelegate</string>
```

**Fix — Created `ios/Runner/SceneDelegate.swift`:**
```swift
// SceneDelegate.swift
//
// This file subclasses FlutterSceneDelegate, which is Flutter's
// UIWindowSceneDelegate implementation. Flutter's app template
// includes this file for all new projects.
//
// FlutterSceneDelegate (the parent class) handles:
// - Creating the UIWindow for the scene
// - Initializing the Flutter engine
// - Connecting the Dart isolate to the scene
// - Managing the Flutter rendering surface lifecycle
//
// This subclass exists so that:
// 1. Info.plist points to a project-owned class (Runner.SceneDelegate)
//    rather than a framework class (FlutterSceneDelegate)
// 2. You can override scene lifecycle methods if needed in the future
// 3. It matches what Flutter's own template generates for new projects
//
// The auto-migration tool (uiscene_migration.dart) does NOT create
// this file — it only rewrites AppDelegate.swift and Info.plist.
// This is a gap in the migration tool as of Flutter 3.41.

import Flutter
import UIKit

class SceneDelegate: FlutterSceneDelegate {
    // No overrides needed — FlutterSceneDelegate handles everything.
    // Override scene(_:willConnectTo:options:) here if you need
    // custom scene setup (e.g., deep linking, state restoration).
}
```

**Fix — Updated `ios/Runner/Info.plist`:**
```xml
<!-- GOOD: Points to the project's SceneDelegate subclass.
     "Runner" is the module name (from the Xcode target).
     This matches what Flutter's template generates for new projects. -->
<key>UISceneDelegateClassName</key>
<string>Runner.SceneDelegate</string>
```

**Fix — Added to `ios/Runner.xcodeproj/project.pbxproj`:**
```
// Three entries were added to project.pbxproj to register
// SceneDelegate.swift with the Xcode build system:

// 1. PBXBuildFile — tells Xcode to compile this file
A1B2C3D4E5F60001SCENE000 /* SceneDelegate.swift in Sources */ = {
    isa = PBXBuildFile;
    fileRef = A1B2C3D4E5F60002SCENE000;
};

// 2. PBXFileReference — registers the file's location and type
A1B2C3D4E5F60002SCENE000 /* SceneDelegate.swift */ = {
    isa = PBXFileReference;
    fileEncoding = 4;
    lastKnownFileType = sourcecode.swift;
    path = SceneDelegate.swift;
    sourceTree = "<group>";
};

// 3. Added to PBXGroup children (Runner group) and
//    PBXSourcesBuildPhase (Sources build phase)
//    so Xcode knows to include it in the build.
```

### 3.3 Conflicting `UIMainStoryboardFile` in Info.plist

**File:** `ios/Runner/Info.plist`

**Problem:** After Flutter's auto-migration added `UIApplicationSceneManifest`, the old `UIMainStoryboardFile` key was left behind. Both were present:

```xml
<!-- BAD: BOTH lifecycle mechanisms present simultaneously -->

<!-- New: UIScene lifecycle (added by Flutter 3.41 migration) -->
<key>UIApplicationSceneManifest</key>
<dict>
    <key>UISceneConfigurations</key>
    <dict>
        <key>UIWindowSceneSessionRoleApplication</key>
        <array>
            <dict>
                <key>UISceneStoryboardFile</key>
                <string>Main</string>           <!-- Scene manifest references Main.storyboard -->
            </dict>
        </array>
    </dict>
</dict>

<!-- Old: Legacy storyboard lifecycle (pre-iOS 13) -->
<key>UIMainStoryboardFile</key>
<string>Main</string>                            <!-- ALSO references Main.storyboard -->
```

**Why this is a problem:**
- On iOS 13+, `UIApplicationSceneManifest` takes precedence
- `UIMainStoryboardFile` is ignored but still triggers some legacy UIKit initialization code
- This can cause `FlutterViewController` to be instantiated in the wrong order
- The scene manifest already references `Main.storyboard` via `UISceneStoryboardFile`

**Fix — Removed `UIMainStoryboardFile`:**
```xml
<!-- GOOD: Only UIApplicationSceneManifest remains.
     The storyboard is referenced inside the scene configuration
     via UISceneStoryboardFile. No need for the legacy key. -->

<!-- UIMainStoryboardFile removed entirely -->
```

### 3.4 Auto-Migrated `AppDelegate.swift` (Understanding, Not a Fix)

**File:** `ios/Runner/AppDelegate.swift`

Flutter 3.41's migration tool automatically rewrites AppDelegate.swift on every `flutter run` if it detects the old pattern. This is **expected behavior** — do not fight it.

```swift
// AppDelegate.swift
//
// AUTO-GENERATED by Flutter 3.41's UIScene migration tool.
// This file is rewritten automatically if it matches the old template.
// Do NOT manually revert to the old pattern — it will be overwritten.
//
// Migration source: flutter_tools/lib/src/migrations/uiscene_migration.dart
// The migration triggers when:
//   1. AppDelegate matches one of the known old templates (5 variants)
//   2. Info.plist does NOT already contain UIApplicationSceneManifest

import Flutter
import UIKit

// @main — marks this as the application entry point (replaces @UIApplicationMain)
// FlutterAppDelegate — Flutter's UIApplicationDelegate base class
// FlutterImplicitEngineDelegate — NEW in Flutter 3.41:
//   Protocol that receives a callback when the Flutter engine is initialized
//   by the scene delegate (rather than by the app delegate directly).
//   This is the "implicit engine" pattern where the scene delegate owns
//   the engine lifecycle, not the app delegate.
@main
@objc class AppDelegate: FlutterAppDelegate, FlutterImplicitEngineDelegate {

  override func application(
    _ application: UIApplication,
    didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?
  ) -> Bool {
    // NOTE: GeneratedPluginRegistrant.register() is NOT called here anymore.
    // In the old pattern, plugins were registered in this method.
    // In the new UIScene pattern, plugin registration happens in
    // didInitializeImplicitFlutterEngine() below, AFTER the scene delegate
    // has created and initialized the Flutter engine.
    return super.application(application, didFinishLaunchingWithOptions: launchOptions)
  }

  // Called by the Flutter framework after the scene delegate creates the engine.
  // This is where plugins are registered in the UIScene lifecycle pattern.
  // The engineBridge provides access to the plugin registry.
  func didInitializeImplicitFlutterEngine(_ engineBridge: FlutterImplicitEngineBridge) {
    GeneratedPluginRegistrant.register(with: engineBridge.pluginRegistry)
  }
}
```

**Old pattern (pre-migration) for reference:**
```swift
// OLD PATTERN — DO NOT USE — will be auto-overwritten by Flutter 3.41
// This is what AppDelegate looked like before the UIScene migration:
@main
@objc class AppDelegate: FlutterAppDelegate {
  override func application(
    _ application: UIApplication,
    didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?
  ) -> Bool {
    GeneratedPluginRegistrant.register(with: self)  // Plugins registered here
    return super.application(application, didFinishLaunchingWithOptions: launchOptions)
  }
}
```

## 5. Debugging Process (Step by Step)

### Step 1: Initial Observation
- App works when launched via `flutter run`
- Swipe-kill → reopen → black screen with Flutter debug banner
- Happens with and without USB debug connection

### Step 2: Log Monitoring (4 Channels)
Set up simultaneous monitoring:
```bash
# Channel 1: Flutter verbose debug session
flutter run -d <UDID> --verbose

# Channel 2: Native iOS logs filtered for app/crash signals
idevicesyslog -u <UDID> | grep -iE "Runner|Flutter|crash|kill|jetsam|GPU|AGX|sandbox|scene"

# Channel 3: Process lifecycle (SpringBoard/RunningBoard)
idevicesyslog -u <UDID> | grep -iE "SpringBoard.*Runner|RunningBoard.*Runner|killed|terminated|SIGKILL|jetsam|watchdog"

# Channel 4: Scene lifecycle events
idevicesyslog -u <UDID> | grep -iE "scene.*connect|UIScene|foreground|background|activate"

# Channel 5: Crash report monitoring
ls -lt ~/Library/Logs/DiagnosticReports/*.ips
```

### Step 3: Log Analysis Findings
- **No SIGKILL, no jetsam, no watchdog termination** — not a traditional crash
- **No .ips crash reports generated** — confirms no native crash
- **GPU sandbox deny errors** (`AGXAcceleratorG13P_B0`) — Skia renderer struggling
- **XPC connection invalidation** on swipe-kill — expected behavior
- **Flutter engine starts** (debug banner visible) but **Dart code doesn't render**

### Step 4: Investigated Theories (All Wrong)
| Theory | Why It Seemed Right | Why It Was Wrong |
|--------|-------------------|-----------------|
| Impeller disabled | GPU errors in logs | Real issue but not the cause of black screen |
| Missing SceneDelegate.swift | Flutter template has it, project didn't | Correct fix but not the cause |
| UIMainStoryboardFile conflict | Both old and new lifecycle present | Redundant but not the cause |
| FlutterSceneDelegate initialization | No local subclass | Framework class works fine |
| Splash screen pattern | Avoid watchdog kill | Dart code never even runs |

### Step 5: Root Cause Discovery
Found in Flutter engine source code:
- `ptrace_check.cc` — explains the ptrace/JIT requirement
- `FlutterViewController.mm` — contains the explicit error message for iOS 14+
- `FlutterDartProject.mm` — debug builds use `kernel_blob.bin` (JIT)
- `devices.dart` — release builds launch without debugger, debug builds cannot

### Step 6: Verification
```bash
flutter run --release -d <UDID>   # Build in release mode (AOT)
# → App launches
# → Swipe-kill
# → Tap icon
# → App relaunches perfectly ✓
```

## 6. Key Takeaways

### For Flutter iOS Development:
1. **Debug builds = JIT = requires debugger = cannot cold-launch on iOS 14+**
2. **Release builds = AOT = no debugger needed = works from home screen**
3. Always test home-screen launch behavior with `flutter run --release`
4. The black debug screen on relaunch is **expected**, not a bug

### For Flutter 3.41 Migration:
1. The UIScene migration tool has a gap — it doesn't create `SceneDelegate.swift`
2. Always add `SceneDelegate.swift` manually after migration
3. Remove `UIMainStoryboardFile` after migration (scene manifest replaces it)
4. Remove `FLTEnableImpeller: false` if it exists (Impeller is default since 3.16)

### For Debugging iOS Flutter Apps:
1. Use `idevicesyslog` over USB for native logs (doesn't work wirelessly)
2. Check for `.ips` crash reports in `~/Library/Logs/DiagnosticReports/`
3. Monitor RunningBoard and SpringBoard logs for process lifecycle events
4. GPU sandbox errors (`AGX*`) usually indicate renderer configuration issues
5. "Lost connection to device" in Flutter logs is normal on swipe-kill
